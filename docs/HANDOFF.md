# HANDOFF — 다른 세션에 넘기는 인계 프롬프트

> 새 세션(클라우드·로컬 어디든)을 열면 **아래 "붙여 넣을 프롬프트" 블록을 통째로 첫 메시지로 보낸다.** 그 아래 `[ ]` 칸만 채우면 된다.
> 새 기획을 맡길 때는 맨 아래 "새 기획 요청서"를 함께 채워 보낸다.

## 1. 붙여 넣을 프롬프트

```text
너는 Godot 4.7.2 팬 프로젝트 「던전 앤 스톤」(소설 『게임 속 바바리안으로 살아남기』의 작중 게임, 비상업)을 이어서 만드는 개발자다.
저장소: rin1015sh/Dungeon-And-Stone-Local. 이번 작업 브랜치: [브랜치 이름 — 없으면 main에서 새로 만든다]

## 시작 순서 (이 순서를 지킨다)
1. `git fetch origin main` 후 작업 브랜치가 main보다 뒤처졌으면 먼저 `git merge origin/main`.
   (다른 세션이 main에 병합한 작업이 빠진 채 진행된 일이 있었다 — 반드시 먼저 합친다.)
2. 읽기: `CLAUDE.md`(작업 규칙·함정·구조) → `docs/CANON.md`(지금 확정된 기획·설정 정본 요약, 문서 우선순위)
   → `docs/PROGRESS.md`의 "현재 상태" 맨 위 몇 항목과 "다음 할 일" → 맡은 주제의 `docs/ASSUMPTIONS.md` 절.
   그림 작업이면 `docs/ART.md`, 1층 몬스터·정수·균열이면 `docs/PROMPT_FLOOR1_V2.md`의 해당 절.
3. Godot이 없으면 내려받는다(CLAUDE.md "클라우드(리눅스) 세션"). 손대기 전에 `GODOT=<경로> bash tools/check.sh`가
   "모든 검증 통과"인지 한 번 확인한다.

## 문서끼리 어긋날 때
날짜가 있는 사용자 결정(ASSUMPTIONS 행·PROGRESS 항목, 같은 주제면 늦은 것) > CLAUDE.md·CANON.md > 실제 데이터 > DESIGN.md
> PROMPT_FLOOR1_V2.md > PROMPT.md. ASSUMPTIONS 행 앞의 "(바뀜 → X)"는 X가 대신한다는 뜻이다.
어긋남을 찾으면 고치기 전에 어느 쪽이 맞는지 위 순서로 판단하고, 판단이 안 서면 사용자에게 묻는다.

## 꼭 지킬 규칙 (자세한 것은 CLAUDE.md)
- 콘텐츠는 data/*.json으로, 수치는 balance.json·render.json으로(코드에 매직 넘버 금지). UI 문자열은 Strings.t + data/strings/ko.json.
- 화면에 부연설명 금지(무엇인지·어떻게 하는지 설명하는 문장·조작 안내·desc_ko 새로 만들기 금지). 결과 문구는 서술형 장면.
- 원작 실명 인물·현실 쪽 설정·원작 문장 복사 금지. 세계관·원작 설정은 문서를 뒤지지 말고 사용자에게 원문을 요청한다.
- 키: 고르기 Enter, 취소 Backspace, 살피기 F(E는 식사). 작은 선택 창은 ChoicePopup.
- 스트레스·기력·마력·신성력 자원은 꺼져 있다 — 쓰지 않는다. 피로도는 Fatigue.
- 1층은 고정 지도(data/maps). 생성기·gen 값을 바꾸면 tools/bake_floor.gd로 다시 굽고, 손으로 놓은 좌표가 어긋나는지 확인한다.
- 모르는 부분은 합리적으로 가정하고 ASSUMPTIONS에 "가정 / 이유 / 바꾸는 방법"으로 남기고 진행한다(세계관 질문만 예외).
- GDScript 정적 타이핑, 스크립트 300줄 이내 지향, 모든 무작위는 Rng.

## 작업 단위
- 시작할 때 PROGRESS "현재 상태" 맨 위에 "범위 / 완료 기준 / 테스트 방법"을 먼저 쓴다.
- 완료 판정 = `bash tools/check.sh` "모든 검증 통과" + 그림·화면을 바꿨으면 캡처해서 직접 본다(헤드리스 테스트는 그림을 검증하지 못한다).
- 끝나면 PROGRESS(한 일·남은 것), ASSUMPTIONS(새 가정·바뀐 행에 "(바뀜 → X)"), CANON.md(정해진 것이 바뀌었으면),
  README(사용자 테스트 체크리스트), CLAUDE.md(새 키·구조가 생겼으면)를 갱신하고, 항상 실행 가능한 상태에서 한국어 짧은 메시지로 커밋·푸시한다.
- PR은 사용자가 요청할 때만 만든다.

## 이번에 할 일
[여기에 할 일을 적는다. 새 기획이면 아래 "새 기획 요청서"를 붙인다. 비워 두면 PROGRESS "다음 할 일"의 "바로 할 수 있는 것"부터.]
```

## 2. 새 기획을 시작하는 법 (AI가 따르는 절차)

새 기획(새 층·새 시스템·새 시설 등)을 받으면 바로 코드를 쓰지 않고 이 순서로 간다.

1. **현재 상태 확인**: `docs/CANON.md`에서 관련 절과 "미결정·보류" 표, ASSUMPTIONS에서 관련 행을 읽는다. 이미 정해진 결정과 충돌하는지 본다(예: "흡수 대기 정수"는 없앤 기능, 스트레스는 꺼진 자원, 1층 지형은 고정).
2. **원작 근거**: 설정이 필요하면 사용자에게 원문을 요청한다. 원문이 없으면 임시값 + `"source": "placeholder"`.
3. **기획서 초안**을 `docs/plans/<짧은 이름>.md`에 쓴다(없으면 폴더를 만든다). 형식:
   - 목표(한 문단) / 원작 근거(받은 원문의 요점 — 문장 복사 금지) / 범위 안 · 범위 밖
   - 규칙과 수치(표 — 임시값 표시) / 데이터 모양(어느 JSON에 어떤 키) / 화면(부연설명 금지 규칙 안에서)
   - 기존 결정과의 관계(바꾸는 결정이 있으면 그 가정 번호) / 사용자에게 물을 것(선택지와 추천)
   - 완료 기준 · 테스트 방법
4. **사용자 확인**: 물을 것이 있으면 선택지와 추천을 들고 묻는다. 정해진 답은 ASSUMPTIONS에 날짜와 함께 "사용자 결정"으로 남긴다.
5. **구현**: 데이터 → 규칙(오토로드 비의존 로직 + 단위 테스트) → 화면(UI 스모크) 순. 레지스트리/핸들러 패턴(효과·이벤트·생성기 = 파일 하나)을 따른다.
6. **검증·문서·커밋**: 위 "작업 단위" 그대로. 기획서 맨 위에 "구현됨(날짜) — PROGRESS 항목" 한 줄을 남긴다.

## 4. 새 기획 요청서 (사용자가 채워서 프롬프트 끝에 붙인다)

```text
## 새 기획 요청
- 이름:
- 하고 싶은 것(한두 문장):
- 원작 근거(관련 원문을 그대로 붙인다 — 없으면 "없음"):
- 꼭 들어가야 하는 것:
- 넣지 말 것:
- 이미 정한 수치·규칙(없으면 "알아서 임시값"):
- 참고 그림·게임(있으면 첨부):
- 이번에 끝내고 싶은 범위(예: 데이터와 규칙까지 / 화면까지 / 그림까지):
```

## 5. 이 프로젝트에서 실제로 겪은 실수 (반복하지 않기)

- main을 받지 않고 시작해 다른 세션의 전투 그림 작업이 빠졌다 → 시작 순서 1번.
- 문서에 "E로 살피기"라고 썼지만 살피기는 F였다 → 키는 `data/input.json`을 직접 확인한다.
- 바뀐 결정의 옛 가정 행을 표시하지 않아 다음 세션이 옛 규칙(흡수 대기·Space 확정·임시 입장 버튼)을 따를 뻔했다 → 결정을 바꾸면 옛 행에 "(바뀜 → X)".
- 큰 지도에서 지도 전체를 매 프레임 훑는 코드가 프레임을 떨어뜨렸다 → CLAUDE.md "1층 지도".
- 문자열 치환으로 코드를 고치다 남은 줄 때문에 UI 스모크가 멈췄다 → 멈추면 `--check-only --script`로 파싱 오류부터.
